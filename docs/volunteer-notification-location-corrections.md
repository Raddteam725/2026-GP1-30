# Volunteer notification, location and Cases corrections

## Cases and Found Reports

Cases now contains only Available Cases / My Cases for Guardian-origin Missing
Cases. Found Reports retain their backend, retention, monitoring and manual/camera
reunification workflows. Unfinished reports remain resumable from Report. The
bilingual regression verifies a saved manual report is absent in Cases and visible
in Report. No live records were changed.

## Replay cause and delivery contract

The previous register_device path redispatched every existing event case whenever
registration, session expiry/auth time, event or location changed. Delivery receipts
were keyed by the FCM registration/token hash. Logout deletes the installation
FCM token; a new token had no receipt for historical events and could receive them
again. This is a code-level replay path; this pass did not provoke a live replay.

Registration now only updates authenticated device/session/location eligibility.
It does not dispatch case history. Event dispatch and the existing recovery worker
remain. Sending also checks the durable notification's created_at against the
registration's created_at: older notifications are not sent to new registrations.
Read notifications are not pushed again. Existing receipt leases/sent_at prevent
repeated successful delivery to the same registration; failed delivery remains
retryable. Stable notification document IDs and read_at are preserved. No history
was deleted and no event ID or domain schema migration was performed.

Foreground presentation additionally remembers handled event IDs in local
SharedPreferences, scoped by authenticated UID and event. Callbacks are serialized.
This survives logout/login and app restart; it is presentation memory, not permission,
server history, or authorization. No names, contact data, tokens or message text
are stored there. History fetches do not generate foreground banners.

These mechanisms prevent application-driven historical replay; FCM itself is not
an exactly-once transport. A server crash after FCM acceptance but before recording
a receipt can still produce a retry. The stable Android notification tag replaces
the same tray item; local foreground memory suppresses repeat foreground banners.

## Android and foreground/background handling

Volunteer sends already use notification + data payloads, Android high transport
priority, stable notification_id/tag and role/case/event metadata. Added an explicit
radd_volunteer_alerts Android channel with IMPORTANCE_HIGH, localized English/Arabic
channel names, and selected it in Volunteer payloads. Guardian payloads/design are
unchanged. The existing POST_NOTIFICATIONS declaration and runtime permission
request remain. Creating a channel does not override user notification settings.

In foreground, onMessage drives the existing in-app banner and targeted refresh.
In background, FCM/Android displays the notification payload; no second local
notification is generated by a Dart background handler. onMessageOpenedApp and
getInitialMessage retain authenticated case navigation. No new Found Report push
category was added. Standard case alerts remain independent of GPS fix availability;
priority still uses the existing valid-location/radius rules and the same case.
Session expiry/revocation/disabled-account checks and normal token renewal remain.

Firebase reference: https://firebase.google.com/docs/cloud-messaging/flutter/receive-messages
Android reference: https://developer.android.com/design/ui/mobile/guides/home-screen/notifications

## Location

Existing mandatory explanation is retained in the blocked participation screen
(Home/Cases/Report), before the user presses Allow Location to request permission.
It explicitly requires permission and enabled services and explains proximity use,
in both languages. No recurring navigation modal was added. With permission/services
valid, the explanatory blocking screen is absent across tabs. Actual permission and
services are rechecked; no onboarding flag can grant participation. The existing
volunteer_location_requested preference only limits automatic permission prompting;
the production workspace initializes without automatically requesting permission.

Denied permission blocks event actions with retry; permanent denial opens app
settings. Disabled services block event actions with location-settings recovery.
Valid permission + enabled services + no current GPS estimate permits participation
and standard alerts, but provides no proximity signal until a valid fix returns.
The position subscription now checks accessGranted explicitly before starting.
The existing authorized Android foreground location service, persistent notification,
stop/revoke/unassign/event-end/logout handling and estimate freshness remain.
