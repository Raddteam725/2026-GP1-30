# Volunteer real-time integration — 2026-09-21

Historical progress report. See [the final real-time implementation report](realtime-final-implementation.md) for current behavior, exact changes and final verification results.

Work continued in the existing working tree. Existing Guardian/Volunteer UI changes were preserved. No commit, push, authentication bypass, AI engine, mock production event, additional Firebase project, or new backend was introduced. No Guardian/Volunteer case was created, cancelled, resolved, joined or handed over by this verification. The real application performed its normal device-registration and durable notification bookkeeping.

1. **Slow new-case appearance.** FCM listeners were installed only after awaiting device registration. Registration repeatedly scanned/dispatched all event cases for all Volunteers on location heartbeats. The workspace also awaited this operation as part of data refresh and dropped incoming refresh requests while busy. List refresh waited for every private photo before publishing cases. The fixes subscribe before registration, decouple registration and photos, restrict device catch-up to the registering Volunteer and actual device/location changes, and queue an additional refresh when an event arrives during a refresh.

2. **“Unable to load current data.”** This was a real error state, not an empty list. Runtime logs contained 30-second HTTP timeouts, including profile, lists and notifications. Backend work and emulator transport were measured separately. A correlated request took over 31 seconds to arrive at FastAPI; other photo requests completed in about 800 ms on the backend but their HTTP headers arrived at the app after 37 seconds. Firebase token retrieval usually took only 1–25 ms. Changing HTTP keep-alive did not solve this and was reverted. The development app now uses the existing `RADD_API_URL` setting with an ADB tunnel to the same FastAPI service. The ADB run completed 196 logged authenticated API requests over about 8 minutes 46 seconds with zero transport exceptions; the slowest completed request was 4,035 ms. This is bounded live evidence, not a guarantee against future network failures. No timeout was lengthened and no error banner was hidden. See the local-run commands below.

3. **Disappearing/reappearing cases.** A failed refresh previously cleared cases and other valid resources. Current-session data now survives transient failures; successfully fetched resources update independently. Successful authoritative empty lists still remove closed cases. A version guard prevents an older refresh or photo response from undoing a newer join/action or restoring protected data after access loss. Duplicate refreshes coalesce; event refreshes arriving during a request are not discarded.

4. **Location permission.** The runtime request was reachable only from the Home action; a previously granted permission did not automatically start location on a new workspace. The emulator already had fine/coarse location permission and notification permission. Startup now resumes granted foreground location, asks on first use, remembers that it asked, permits explicit retry after denial, and offers Settings for permanent denial or disabled location services. Background location remains stopped, inaccurate fixes are not used for priority, and the existing 500 m / Guardian-confirmed location rules remain unchanged.

5. **Foreground/background notifications.** Real FCM events now produce a dismissible Radd-styled banner in the root overlay, including while camera/QR routes are open. Arabic RTL and English LTR are supported. A newer important event replaces an undismissed banner; both remain in history. New/priority actions load the exact case through the authenticated API. Closed/matched events open history when the recipient no longer has case-detail access. Background/terminated delivery still uses Android FCM notification payloads, with startup/open listeners installed before token-registration work. As explicitly requested, the existing ID-token-expiry eligibility limit remains: account Active alone does not extend push delivery beyond the registered token's expiry.

6. **Durable history and deduplication.** Notifications are stored under `users/{uid}/volunteer_notifications/{caseId-eventSuffix}` before FCM delivery, even when no eligible device exists. Stable IDs are included in payloads, used for foreground deduplication within the authenticated workspace, and used as Android notification tags. Per-device delivery receipts and leases prevent repeated sends on ordinary retries. History is authoritative server data; the banner does not insert fabricated client records. Existing 24-hour terminal-case retention remains unchanged and expired/scrubbed case notifications are not recreated.

7. **Guardian creates a case.** The existing create/report hooks dispatch the real new-case event; eligible accounts receive durable history and eligible devices receive FCM. Receipt immediately displays the foreground banner and triggers list/history refresh, with a queued follow-up if a refresh is already running. Missing/expired case photos no longer block lists or cause repeated known-404 requests: the backend supplies a safe availability flag, and actual photo access still checks authorization/retention.

8. **Guardian cancels.** The existing `cancelled` transition now dispatches a cancellation event. Active Volunteers who previously received the case or joined it are included; unrelated newly created accounts are not. The event is durable, retryable through the existing local jobs, and distinct from resolution/reunification. Authoritative active lists omit the cancelled case.

9. **Guardian resolves / match / reunification.** The existing `resolved` transition reports that the Guardian found the person; `match_confirmed` continues to mean verification/handover are pending. Successful verified handover emits a separate `reunited` notification. Existing QR/alternative verification and handover checks remain enforced. Closed history statuses are handled without indexing the workflow enum with an invalid value.

These are observed development measurements, not performance guarantees. Independent resources load concurrently; photos enrich later; case opening does not wait for photos; notification read/join/report actions no longer wait for unrelated full refreshes. Server-authorized action responses update local state immediately. Debug request IDs and token/header/total timings permit correlation without logging credentials or payloads. Existing 20-second foreground reconciliation was not made more aggressive; immediate refresh is event-driven.

## Local development run

### Authenticated notification session follow-up — 2026-09-21

The app now listens to Firebase `idTokenChanges()` as well as FCM token rotation. Same-account ID-token renewal re-registers the device automatically; logout/account switch ends the binding, and a new authenticated workspace establishes a new binding. Requests from an old repository cannot use another account's credentials. Known invalid Firebase-session errors enter the existing protected-data clearing/logout path. A registration completing after closure is unregistered again.

The backend stores only the verified token's expiry and `auth_time` with the existing registration, not the ID token. Before push delivery it checks Firebase Auth account disablement and the revocation boundary. Expired, revoked and disabled sessions are ineligible; lookup failure fails closed and preserves retryable history. Renewal of an expired registration triggers catch-up without duplicate delivery. Existing foreground banners, stable event IDs, history, immediate refresh and Guardian closure hooks remain intact.

Final automated checks: `flutter analyze` passed; full Flutter suite **137 passed**; full backend suite **153 passed**, **47 upstream deprecation warnings**; debug APK built successfully; `git diff --check` passed. Added isolated tests cover normal renewal, logout/re-login, account switch, auth-stream errors, revocation/disablement, failed Auth lookup and retry, and immediate catch-up after expiry. These tests do not revoke or disable real accounts.

Live checks: installed the APK preserving the existing login; authenticated FCM registration returned HTTP 200. Read-only Firebase Admin verification found one real active Volunteer registration with a future expiry and a valid server-bound `auth_time` meeting the real Auth revocation boundary; the Auth account is enabled. No real case/user state was changed to manufacture an event. No new IAM/API configuration was needed. Actual hour-boundary refresh, coordinated logout/re-login push delivery and background/terminated-device behavior remain device tests; previously dispatched OS notifications cannot be recalled by a later authorization check. Local retention jobs remained disabled during this diagnostic run. No commit or push was performed.
